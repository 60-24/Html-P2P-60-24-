Core Concept

P2P 60-24 is a decentralized, modular P2P system governed by a formal Constitution (v0.4.0) and Architecture Decision Records (ADRs).

Key innovation: Task-Oriented Ontology (ADR-012) — Tasks are atomic, immutable units of work; Agents are fungible executors; no centralized orchestrator.

Prime Axioms (A1–A10)

A1 — Identity
Każda Entity ma unikatową, kryptograficznie weryfikowalną tożsamość (Ed25519).
A2 — Consistency
Niezmienniki nigdy nie mogą być naruszane. Global consistency > local autonomy.
A3 — Adaptation
System uczy się z doświadczenia (Memory, Reputation). Nie sztywny.
A4 — Diversity
System toleruje wielość podejść do tego samego problemu (o ile tą samą ontologią).
A5 — Evolution
System ewoluuje bez przerwania usługi (Deprecation ≥ 3 epochs).
A6 — Local Autonomy
Każdy moduł ma prawo do lokalnej decyzji w swoim Bounded Context.
A7 — Cooperation
Agenty współpracują dobrowolnie. Nagradzane (Trust ↑), kary za defection.
A8 — Observability
Każdy stan, event, decision musi być loggowany i queryowalny (EventBus).
A9 — Reversibility
Każda decyzja musi być reversible (rollback) lub auditowalna (EventBus).
A10 — Minimal Complexity
Dodaj Feature/Module tylko jeśli rozwiązuje konkretny problem.

⚡ Reguła Rozstrzygania Konfliktów

Global Consistency (A2, A8, A9, A10) > Local Autonomy (A6)

Chyba że architektura jawnie definiuje granice autonomii (Bounded Context). Dzięki temu moduły działają niezależnie, ale nie mogą naruszać niezmienników systemu.

MiniKernel & Build Phases

MiniKernel (5 Core Services)

  • Identity — Ed25519 pubkey management, signing (✅ ADR-001)
  • Transport — UDP:6024 P2P mesh (✅ ADR-002)
  • EventBus — Immutable log, quorum signing (🔄 ADR-003)
  • State Store — Versioned snapshots, queryable (🔄 ADR-004)
  • ModuleLoader — Hot-reload (📋 ADR-005)

Six Build Phases

  • Phase 1: MiniKernel (2–4 weeks)
    Single-node binary. Identity, Transport, local EventBus, State.
  • Phase 2: Distributed Memory (3–6 weeks)
    Replicated state, 3f+1 quorum, Byzantine FT, gossip protocol.
  • Phase 3: Agent Runtime (4–8 weeks)
    Task scheduling, Result submission, Memory extraction, Reputation.
  • Phase 4: Model Runtime (4–8 weeks)
    LLM integration (Claude, GPT), prompt templates, output validation.
  • Phase 5: Reputation & Economy (6–10 weeks)
    Token allocation, slashing, auction (Need ↔ Offer pricing).
  • Phase 6: OneClick Package Builder (2–4 weeks)
    Docker, Web dashboard, CLI, cloud deployment.
